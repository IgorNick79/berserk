# Stage 2: серверное резервирование инстантов

План скорректирован 27 октября 2026 после согласования Stage 1.

## Область этапа

Одна сохраняемая модель `battle.instant_reservation`: период конкретного хода,
владелец хода, лимит/расход платных остановок, поколение запроса, причина
`paid`/`free`, контекст бесплатного запроса и состояние `idle/requested/granted`.
Стек остаётся существующим `turn_instant_stack`; универсальный `resume_choice`
не создаётся. UI и конкретные обязательные окна не подключаются.

1. Платный запрос регистрируется пассивным игроком через `reserve_instant`.
   Отмена — `cancel_instant_reservation`, отказ от уже предоставленной пустой
   цепочки — `decline_instant_priority`. Все команды используют существующие
   POST/journal/expected_version/блокировку партии.
2. После завершённой игровой команды и её синхронных continuation, когда нет
   обязательных выборов, сражения, фаз хода и вложенных продолжений, запрос
   автоматически открывает штатный turn-стек с приоритетом запросившего игрока.
   Регистрация/отмена/настройки/опрос состояния не являются границами действия.
3. Платная попытка расходуется один раз при успешном открытии стека. Отказ
   разрешён только до первого объявления. После объявления используются обычные
   пас/выборы/разрешение. Возврат определяется завершением всей цепочки, включая
   вложенные сражения, а не только исчезновением первоначального стека.
4. Бесплатный запрос имеет тот же жизненный цикл, но не расходует лимит.
   Для Stage 3 предусмотрен серверный вход с проверенным происхождением выбора;
   клиентский payload не может назначить бесплатную стоимость. Пока конкретные
   окна не подключены, запрос из pending отклоняется, а не ошибочно тарифицируется.
5. Незадействованный запрос снимается при завершении хода; новый бюджет
   создаётся в штатном начале следующего периода. `battle.turn` недостаточен:
   он увеличивается только при переходе к host. Старый request_id не подходит
   для отмены/отказа нового запроса.
6. Requested не останавливает таймер. Стек использует существующий
   BattleWaitResolver/TurnTimer. Сервер блокирует обычные действия обоих игроков
   до завершения выданной цепочки; дочерние обязательные команды сохраняются.

## Проверки

Unit: регистрация/повтор/отмена/старый токен, расход и восстановление лимита,
переходы host/player, отказ, LIFO и два паса, сериализация, истечение времени,
невозможность выдачи при pending/combat/continuation, бесплатный серверный вход,
отсутствие права клиента назначить free, возврат после вложенных действий.

Изолированная InnoDB: два процесса с отдельными соединениями, одинаковой
expected_version и конкурирующими reserve/action; конкурентные повторы одного
command_id; отказ/отмена против запуска; атомарный rollback и повтор. Проверяется
реальный GameRepository/CommandJournalRepository, а не SQL-имитация.

Базовые регрессии: turn/combat стеки и фазы, CombatContinuation, таймер,
информационные подтверждения, action resolution. Пробел SwampQueenSummonChoice
устраняется адресно до проверки владельцев ожиданий, без изменения способности.

Stage 3 требует отдельного согласования.
