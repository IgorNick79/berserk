Этап 1 реализован и протестирован до этапа 2. TempleWarrior::rangedBlock вызывается для uchr в отдельном обработчике и для shot/throw в resolveDamage после штатного объявления атаки и формирования результата, до эффектов попадания и урона. Дополнительный первичный бросок принадлежит защищающейся карте и использует CardRoll. Результат хранится в strike.temple_defense; 5–6 завершают заблокированное действие с поворотом источника (если требуется), не применяя hit-эффекты/урон/ответ. Остальные карты не получают дополнительного броска. BattleScreen дополняет существующее отображение подписанными кубиками атаки и защиты и текстом блокирования, используя DiceValue.

Этап 2: StrikeResolver::resolve бросает обычные первичные кубики сторон, затем дополнительный кубик каждого участника с combat_choose_two. Результаты сохраняются в strike.temple_rolls; если значения различаются, pending_temple_dice содержит владельца, сторону, значения, уникальный id и очередь второй стороны (если оба участника имеют способность). Противник уже бросил кубик и виден до выбора. Одинаковые значения выбираются автоматически. Отсутствующий защитный бросок не создаёт ни дополнительного броска, ни pending.

TempleDiceChoice проверяет владельца, id и допустимое значение; устанавливает исходный кубик, а после последнего выбора вызывает StrikeResolver::continueTempleDice. В этот метод вынесена существовавшая часть resolve: штатные OVA/OVZ/clumsy → таблица → окно dice-инстантов → main → разрешение. Новый action не создаётся, кубики не бросаются повторно. Ловец работает с выбранным значением и сохраняет прежний переброс Dice::roll по одному кубику каждой стороны; passive/pending не повторяются.

В pending показаны графические DiceValue: сгруппированные кубики Воина храма и кубик противника. Только владелец получает две кнопки. После выбора исходные кубики сохраняются в отдельной подписанной строке: отброшенный приглушён, выбранный выделен. При перебросе показывается актуальное действующее значение, первоначальные результаты не изменяются. Используется flex-wrap для узкой ширины. InfoPanel не менялся.

Фрагмент prop в temple-warrior.prop.json содержит только два ключа уникальных способностей; его следует объединить с остальной конфигурацией карты, если она есть.

Ограничения покрытия: реальные два HTTP-клиента и серверный деплой не проверялись. Нет отдельного сценария с двумя Воинами храма одновременно; для этого предусмотрена очередь, но сценарий пока не добавлен. Браузерный тест проверяет первоначальный выбор; выбранный/приглушённый вид и два кубика дальней атаки пока проверены чтением разметки, а не отдельными браузерными кейсами. Не покрыты исчерпывающе платные или условно предоставленные дальние атаки в сочетании с блокированием: требуется отдельная проверка ресурсов и once-per-turn. Эти ограничения не следует выдавать за пройденные интеграционные сценарии.

Конфигурация ranged_block_roll — объект с явными types и block_on. Булево true не включает защиту; список атак и успешных значений больше не зашит в обработчик. Проверены неперечисленный тип без расходования кубика и нестандартное значение блокирования из конфигурации.
