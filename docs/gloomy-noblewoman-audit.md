## Проверенные механизмы

### Лечение

Нет общей точки ДО изменения HP. ActionResolution::healed принимает before и вычисляет разницу с УЖЕ изменённым HP. Он не умеет приостановить инициирующее действие и не видит положительное лечение полного существа. Recorder::healed также фиксирует уже совершившееся изменение. Это наблюдатели, не подходящая точка для Дворянки.

Пути, требующие согласованной границы:

| Файл | Путь | Особенность продолжения |
|---|---|---|
| ActionResolver | resolveHeal | стоимость, закрытие, poison removal, жетон Сшивателя, результат/ACK |
| ActionResolver | chooseMultiHeal | несколько целей, сводный результат, очередь замен Вожака |
| ActionResolver | chooseKoboldHeal | закрытие выбора, продолжение исходного удара |
| ActionResolver | resolveLifeGift | лечение союзника и независимая часть дара |
| ActionResolver | chooseWildHealerHeal | движение уже произошло, нельзя повторять его |
| ActionResolver | applyShaksiEffect | продолжение броска/выбора Шакси |
| DamageResolver | applyDamage/vampire | внутри незавершённого повреждения, ещё возможны смерти/цепочки |
| DamageResolver | deadeat, flushDeadeatQueue | очередь трупоедства, возможное увеличение hpMax отдельно |
| DamageResolver | triggerOnDeath/chooseOnDeathTarget | живой/умерший источник и очередь смертей |
| StrikeResolver | defender_heal | прерванный удар до дальнейшего разрешения |
| StrikeResolver | on_strike_self_heal | продолжающийся удар и ответка |
| Engine | applyInstantEffect heal/heal_turn_wounds | InstantProcessor сразу после вызова фиксирует результат и двигает стек |
| Engine | regeneration | отдельный путь без ActionResolution::healed |
| TurnPhaseProcessor | regeneration/turn_end heal | нельзя перейти к следующей задаче до выбора |
| ValhallaProcessor | heal | только Recorder, нет общей реакции лечения |
| WoundTransferProcessor | восстановление донора | нельзя повторять перенос и уже определённые независимые раны |

Отдельно исключаются из событий лечения: установка hp при возрождении/инкарнации/призыве, начальная установка hp сценария, start.get_hp (увеличивает и hpMax), техническая нормализация hp. Регенерация, вампиризм и трупоедство в имеющемся коде уже помечаются как лечение хотя бы в одном из своих путей; это надо согласовать для всех эквивалентных путей.

### Вожак

CardStats::canHealInsteadWound проверяет effectiveProp, отсутствие ран и индивидуальные 3 использования за ход. Проверки и pending продублированы в active heal, multiheal, Wild Healer и defender heal. Прямой heal инстанта, часть пассивов и другие перечисленные пути обходят их. chooseHealInsteadWound умеет отложенные remaining и отдельный waiting_resolve_after_heal только для частного боевого случая.

Поэтому переносить всю обработку в ActionResolution::healed нельзя: он вызывается слишком поздно. Просто откатить HP и поставить pending тоже нельзя: к этому времени уже могли завершиться подэффекты, потребиться ActionResolution-токен, сдвинуться стек, выстрелить реакции и смениться фаза.

### Pending

ChoiceRegistry, PanelSpec, BattleWaitResolver, InformationalWaitManager, CombatContinuation и продолжения InstantProcessor можно переиспользовать. Однако CombatContinuation сейчас сохраняет боевые кадры и стек инстантов, а не место исполнения внутри applyDamage/цикла смерти/задачи конца хода. Создание pending само по себе не останавливает синхронный вызывающий код. Replay команды целиком потребовал бы воспроизведения оплаты/случайных чисел/смертей и запрещён как рискованный обход.

### Характеристики и подавление

zor уже есть в PermanentFeatures и не требует нового механизма. vampire уже обрабатывается DamageResolver для strike/tap/magic/execute. Использовать его повторно.

computeArmor принимает armor как объект с value; целое armor=1 не даст броню. Однако effectiveProp отфильтровывает armor при Потере памяти. Проверено: armor.value=1 превращается из 1 в 0 после подавления, zor остаётся. Нельзя просто объявить весь ключ armor постоянным: так сохранились бы также уникальные условные и строевые источники брони других карт. Нужно различать собственную безусловную постоянную броню и выдаваемые уникальные бонусы, сохранив последние подавляемыми.

hp_max_override уже используется вампиризмом и CLI seed/test_cards. Но реальные createDeckInstances и создание руки назначают hpMax из health, без override. Поэтому одних vampire=true/hp_max_override=12 в prop недостаточно, чтобы все пути лечения видели максимум 12. Требуется единое получение максимума при создании экземпляра с сохранением стартовых 8 HP (без автоматического лечения на 4). Это характеристика, не активная способность.

## Минимальное безопасное решение

1. Ввести узкую операцию лечения с сериализуемым контекстом: operation_id, turn, active_owner, source_id, target_id, declared_amount, modified_amount, actual_restored, список проверок Дворянок, stage и явный return_to. Не хранить замыкания/PHP-стек.
2. Перевести перечисленные реальные пути лечения на эту границу. Вызвавшие обработчики должны явно прекращать текущий этап при pending и продолжать с сохранённого следующего этапа, а не повторять исходную команду. Начать с active heal/instant/боевого vampire и постепенно покрыть остальные, не объявляя карту готовой до полного покрытия.
3. Счётчик первого действия лечения хранить на уровне GameState.battle для всего хода, включая отсутствие Дворянок/подавление/HP=8. Отмечать первое объявленное лечение до выбора. Для multiheal — одна идентичность действия и детерминированные составляющие; не считать каждую запись HP отдельным первым действием. При смене хода новый turn-key. Восстановление при возрождении не трогает счётчик.
4. Проверять активную, затем пассивную Дворянку независимо от источника лечения. При подтверждённом конфликте double/block разрешать автоматически в ноль и сохранять объяснение как результат операции, не создавая фиктивных ручных решений. В остальных случаях pending владельца с токеном этапа; применение/отказ потребляют текущую возможность.
5. После Дворянок при modified_amount=0 не предлагать замену Вожаку. При положительном H проверить Вожака-цель; при полном HP предложить существующую замену раной на H. При отказе — обычное ограниченное лечение. Затем завершить независимые части исходного действия один раз и вернуть управление инициатору.
6. Сохранить отдельные значения H, modified H и actual restored и порядок событий для проверок; не выводить решение игрока там, где сработал автоматический конфликт. Показать сообщение через существующий PanelSpec/результат операции без изменения InfoPanel.
7. Адресно исправить представление постоянной собственной брони и характеристик hpMax при создании, не сохраняя подавленные строевые бонусы других карт.
8. После этого подключить единый интеграционный JSON runner: обе Дворянки и оба Вожака, источники лечения, раненые обычные цели И полные Вожаки для значимых замен, шесть пар HP, сценарии A–J. Дать тот же состав как LuckTest JSON для воспроизведения. JSON начальной расстановки без команд/ожидаемых событий не является достаточным интеграционным тестом.

Такое изменение ограничено разрешением лечения, но затрагивает несколько семейств продолжений. Оно существенно шире добавления prop одной карты. Без этого расширения нельзя честно выполнить требование единого lifecycle и двух Вожаков.
