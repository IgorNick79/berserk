# Комната ожидания Berserk

## Read-only аудит

- Отдельная комната — тот же `www/lobby.php?room=N`, её представление формировал `www/assets/js/lobby.js` внутри центральной панели лобби.
- Сервер возвращает разрешённые детали через `LobbyStore::read`: создатель, текущий кандидат/принятый игрок и приглашённый имеют разные роли. Закрытая комната скрыта от остальных в списке и прямом маршруте.
- Заявка (`open`), подтверждение (`accept`), отказ (`reject`) проходят существующий контроллер с CSRF, версией и идентичностью заявки. `RoomTransaction` создаёт GameState только после принятия заявки.
- Клиент опрашивает ту же комнату каждые 1500 мс, отбрасывает устаревшие версии и ответы, блокирует повторное действие. При потере ответа восстанавливает состояние чтением; mutation автоматически не повторяется. Созданная игра открывается прежним автоматическим переходом.
- Боевая панель использует ширину `min(440px,45%)`, поверхность и рамки из четырёх существующих тем, верхний информационный блок и нижнюю зону действий.
- `GameMenu` является общим компонентом; контекст `preparation` обеспечивает «В лобби», а Debug без контекста партии не появляется.

## Реализация

Экран комнаты получил отдельное представление `lobby-room.js`, вызываемое существующим контроллером лобби. Слева одна общая иллюстрация, справа — тематическая информационная панель с двумя местами игроков, фактическими состояниями, read-only параметрами и нижними действиями.

Для правой панели переиспользованы существующие CSS темы боя: расширена область действия четырёх правил оформления. Геометрия боя и остальные боевые селекторы не менялись. Общий `GameMenu` и обработчики настроек не дублируются; смена темы применяется и к комнате.

Подтверждённая необходимость изменения `LobbyStore` ограничена четырьмя строками закрытой проекции: тип доступа вычисляется из существующего приглашения, лимит хода читается из сохранённого `setup_json`. Отсутствующее историческое поле означает 180 секунд; явный 0 означает отсутствие ограничения. Публичная проекция, SQL выборки, доступ и переходы комнаты не менялись. Настройки/debug/ключ создания наружу не передаются. `RoomTransaction`, создание GameState, Engine, таймеры и pending не менялись.

Изображение и структура панели не пересоздаются при polling. Только изменившиеся значения обновляются текстом; элементы управления меняются при изменении версии/роли/доступности. Действия вызывают прежние callbacks. Созданная игра открывается автоматически, как и раньше.

На desktop доступна одна прокрутка содержимого информационной панели при закреплённой нижней зоне. На узком экране иллюстрация компактнее, колонки складываются, используется прокрутка документа. Иллюстрация статична: отдельная анимация свечи не добавлялась.

## Чат комнаты

После отдельного разрешения реализован контекст переписки комнаты без раннего создания GameState. Повторно используются существующие `game_chat.tpl`, `battle-chat.css`, иконки и клиентский `battle-chat.js`. В общем JS добавлен выбор endpoint/контекста и очистка устаревшего контекста; для боя сохранены URL `index.php?game=...`, хранилище GameChat, подписи ходов, уведомления и правила отправки. В `www/index.php` обновлена только версия JS для сброса кэша.

Новый `RoomChat` работает с БД лобби через отдельные таблицы `lobby_chat_messages` и `lobby_chat_reads`; существующие таблицы боевого чата и GameChat не изменены. Очистка текста и проверка курсоров переиспользуют методы GameChat. Сообщения — до 1000 Unicode-символов, включая эмодзи; HTML не исполняется. Проверяются CSRF, методы, параметры, принадлежность к текущему диалогу, идемпотентный request_id и ограничение 1 сообщение в секунду от аккаунта в комнате. История загружается страницами по 50 сообщений, прочтения монотонны.

Доступ и выбор собеседника проверяются под блокировкой строки комнаты в той же транзакции, что и чтение/запись чата. Новых UPDATE комнаты, записей GameState, команд или событий Recorder нет. Состав диалога: создатель и приглашённый (закрытая открытая комната), текущий кандидат (заявка) либо принятый участник (игра создана). В открытой комнате без кандидата создатель может открыть панель, но ввод отключён с объяснением ожидания второго участника.

Данные разделены по `(room_id, peer_account_id)`. Новый кандидат не получает прошлые сообщения, непрочитанные отметки или курсоры другого кандидата. Отправка/прочтение требуют актуальный идентификатор контекста; прежний контекст отклоняется 409. У публично отклонённого кандидата доступ прекращается. При возвращении того же аккаунта сохраняется его прежняя переписка с создателем.

Общий клиент обновляет чат независимо от комнаты. При смене собеседника очищаются старые сообщения, курсоры и неподтверждённый черновик; ответы старого поколения не подмешиваются в новый диалог. Утерянный ответ на отправку повторяется вручную с тем же request_id. Метки непрочитанных, Enter/Ctrl+Enter, Escape, кнопка отправки и пагинация используют прежний контроллер.

После принятия заявки история комнаты остаётся доступной участникам через API для чтения. Неподтверждённый уже сохранённый request_id получает прежний ответ; новые сообщения комнаты после старта запрещены. Переход в игру остаётся автоматическим. Переписка комнаты не переносится в боевой журнал сообщений; боевой чат продолжает работать как прежде.

## Отмена собственной заявки

Кандидату в ожидании подтверждения добавлена кнопка «Отмена». Новый action `withdraw` использует существующую транзакцию `RoomTransaction::run`, SELECT FOR UPDATE комнаты, ожидаемую версию и точный `candidate_request_id`. В закрытой проекции ID заявки теперь возвращается также самому её кандидату; посторонние и публичный список его не получают. Создатель не может отменить чужую заявку этой командой.

Успешная отмена очищает кандидата и nonce, переводит комнату в существующее состояние open и увеличивает версию. Настройки, приглашение и остальные данные сохраняются. Игра не создаётся. Клиент возвращает игрока в лобби; ответ отмены не пытается читать комнату, доступ к которой публичный кандидат уже утратил. При потере ответа клиент восстанавливает итог чтением, а не повторением POST. Собственная отмена не вызывает ложный сигнал о решении создателя.

Конкуренция: если отмена обработана первой, принятие старой заявки получает 409 и не создаёт GameState. Если принятие обработано первым, отмена получает 409 и не затрагивает созданную игру. После повторной заявки её новый nonce защищает от отмены/принятия старым запросом. Повтор уже выполненной отмены отклоняется без второй мутации; у уже утратившего членство публичного кандидата это может быть 403.

Проверены CSRF, запрет отмены создателем и посторонним, собственный ID заявки, обе последовательности accept/withdraw, повторные запросы и старый nonce, сохранение закрытого приглашения и повторная заявка. Четыре параллельных HTTP-гонки с барьером дали один успешный запрос и один 409; число новых игр равно 0 при выигрыше отмены и 1 при выигрыше принятия.

Итоговый повторный прогон: 227 HTTP/БД-проверок, 61 браузерная проверка комнаты, прежние проверки чата/мастера/меню. Кнопка и возврат в лобби проверены в браузере с имитацией потери успешного ответа: ровно один POST, состояние восстановлено, лишнего звука решения нет. PHP lint, JS syntax и git diff --check прошли. Первый общий браузерный запуск остановился по timeout загрузки существующей подготовки; повторный прогон прошёл полностью без изменения проверок.
