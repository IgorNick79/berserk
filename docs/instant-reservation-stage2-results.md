## Состояние и переходы

`battle.instant_reservation` сохраняется обычными GameState::toArray/fromArray:

```json
{
  "period_id": 1,
  "turn_owner": "host",
  "limit": 2,
  "used": 0,
  "generation": 1,
  "status": "requested",
  "request": {
    "id": "ir:123:1",
    "owner": "player",
    "reason": "paid",
    "origin": null
  },
  "ended": false
}
```

`snapshot()` добавляет вычисляемый remaining, не изменяя GameState.
Идентичность периода относится к конкретному ходу стороны, а не только к номеру
раунда battle.turn. При новом периоде used=0, limit берётся из конфигурации.
generation не сбрасывается; идентификатор старого запроса не совпадёт с новым.
Повторный вызов начала того же незавершённого периода не восстанавливает квоту.
Для старых партий без нового поля поддержана чистая проекция и инициализация
при первом принятом запросе.

Переходы:

- idle → requested: запрос зарегистрирован, расход 0, обычное время продолжается.
- requested → idle: отмена; конец хода; недоступность способностей на границе;
  истечение времени на границе; окончание партии. Без расхода.
- requested → granted: автоматически открыт штатный turn_instant_stack с первым
  priority=request.owner; платный used увеличен один раз, бесплатный не меняется.
- granted → idle: отказ до первого объявления либо завершение всей штатной
  цепочки, её результатов и дочерних продолжений. Расход не возвращается.

Granted сохраняется на протяжении вложенных сражений и подтверждений, а не
только до исчезновения исходного turn_instant_stack. Для этого новый корень
подключается к существующим frames/stacks CombatContinuation через blocked().
Отдельного движка эффектов или универсальной приостановки pending нет.

## Команды

Все команды идут через прежний `POST ?game=ID&ajax=battle_command`, с авторизацией,
CSRF, command_id и expected_version. Нового endpoint и обходного UPDATE нет.

| cmd | Параметры | Серверное поведение |
|---|---|---|
| reserve_instant | period_id | Пассивная сторона, действующий период, обычная безопасная ситуация, доступные turn-способности, неизрасходованный лимит. Повтор requested возвращает тот же запрос. |
| cancel_instant_reservation | request_id | Только владелец своего requested; старый токен и granted отклоняются. |
| decline_instant_priority | request_id | Только владелец текущего приоритета в своём пустом ordering-стеке, до объявления и выбора цели. После передачи приоритета сопернику отменить его право нельзя. |

После открытия используются существующие play_turn_instant, choose_instant_pick,
pass_turn_instant, turn_instant_result_ok и дочерние обязательные команды.
Прежний open_turn_instants остаётся механизмом активного игрока.

При granted Engine отклоняет новые move/jump/gain_coin/action/uchr/strike/end_turn/
open_turn_instants обеих сторон. Внутренние разрешения вызывают свои штатные
резолверы, а нужные пользователю дочерние выборы остаются достижимыми через реестр.
Сдача и существующая пауза сохраняются.

## Бесплатная причина: что готово и что отложено

В состоянии сохраняются reason=free и origin={source, choice_id}. Для Stage 3
предусмотрен серверный вход `InstantReservation::request(..., $freeOrigin)`.
Он сверяет источник ожидания и required_players через BattleWaitResolver,
требует серверную идентичность выбора, не снимает и не завершает pending.
Вызов поверх strike/combat_continuation отвергается. Такой запрос разрешён и
при исчерпанном платном лимите; на безопасной границе открывается тот же стек
без изменения used.

Клиент не передаёт $freeOrigin: reason=free в POST не даёт бесплатности, limit
из POST тоже не используется. Конкретные pending-окна пока не подключены:
первичный запрос из них возвращает instant_reservation_pending_not_connected.
Это защищает от ошибочного платного расхода вместо ещё не подключённого free.
Бесплатный жизненный цикл проверен через доверенный серверный вход в тестах;
готовность всех игровых pending здесь не заявляется.

При ранее зарегистрированном requested повтор команды не меняет его исходную
причину, поколение и стоимость. Можно отменить запрос до выдачи. Отдельных
очередей paid и free нет, одновременно ожидает только один запрос.

## Точная безопасная граница Stage 2

Проверяется конец успешной Engine-команды после CoinAbilities::advance,
CombatContinuation::settle, MatriarchOrderProcessor::advance и завершения
start_resolution; перед TurnTimer::reconcileWaiting.

Для выдачи одновременно необходимы:

- Та же сторона хода/период, battle без победителя и паузы, не истёкшее время.
- Нет ожидания BattleWaitResolver, strike, turn_phase, turn-стека/результата.
- Нет combat_continuation, matriarch_order, coin_post_combat_queue/continuation,
  informational_wait/pending и любого непустого pending_*.
- У запросившего по-прежнему есть применимый turn-инстант.

Поэтому многошаговое действие завершается полностью; выдача не происходит
между выбором цели, оплатой, нанесением урона и дочерним сражением. Конкретные
более ранние границы существующих continuation относятся к будущему Stage 3.
Combat dice/main/wounds не прерываются новой turn-цепочкой.
Регистрация, отмена и отказ не являются поводом выдать следующий резерв.
Настройки игрока, команды паузы, опрос и навигация не проходят этот игровой путь
выдачи. На end_turn старый запрос снимается без расхода; системные окна остаются.

### Конкурентность и атомарность

1. Reserve первым держит lock партии: он commit без расхода; конкурирующее
   действие со старой версией conflict, Engine для него не вызывается. Повтор
   действия с актуальной версией выдаёт ровно один резерв.
2. Action первым держит lock: действие завершается целиком; поздний reserve
   conflict. Повтор reserve ждёт следующего действия и не вмешивается задним числом.
3. Два процесса с одним command_id: второй видит processing, затем committed;
   повторно Engine не вызывается. generation и версия увеличены один раз.
4. Cancel/grant в обоих порядках: победитель commit, второй conflict; расход
   следует только принятому порядку. Отказ после grant не возвращает попытку.
5. Ошибка записи после применения действия откатывает JSON, квоту, стек,
   запись истории и terminal status журнала. Повтор коммитит одну остановку.
6. Четыре реальных HTTP-гонки: оба запроса достигли processing, пока внешнее
   тестовое соединение удерживало строку games; затем lock снят. В каждой один
   committed и один HTTP 409/conflict. Проверены оба фактических порядка победы.
7. Проверены реальные HTTP replay, отказ, старый request_id с новым command_id,
   конфигурации лимита 1/0 в изолированной копии и сохранение уже начатого бюджета.
8. SQL и финальные HTTP-fixtures используют journal_schema=1 и обязательный
   Recorder. Пять команд reserve/cancel/reserve/action/decline имеют пять
   атомарных history batches; технические команды не создают ложных history gaps.

## Риски и границы результата

- Stage 3 ещё должен подключить разрешённые mandatory окна и определить их
  фактические границы/идентичности. В Stage 2 нет массовых адаптеров и нет
  универсального resume_choice.
- Единый UI, стоимость на кнопке, показ remaining и клиентская проекция
  instant_controls относятся к следующему UI-этапу. Серверные команды доступны
  и проверены, но новых кнопок в интерфейсе сейчас нет.
- Общие условия prop для self-целей и полный контракт ресурсов combat требуют
  дальнейшей проверки доступности. Здесь добавлены только необходимые общие
  проверки живого/раскрытого источника, без изменений карт/no_close.
- Граница намеренно консервативна: неизвестное или незавершённое продолжение
  откладывает выдачу, не получает право прерывания.
- При обязательном Recorder старое gain_coin в синтетическом fixture может
  отмечаться uncovered_command; это существующий пробел истории вне задачи.
  Он зафиксирован и не исправлялся. Новые технические команды покрыты отдельно.
- Изменения не опубликованы, commit/push/deploy не выполнялись. Рабочая БД и
  её настройки не изменялись. DDL/учётные записи создавались только на отдельном
  тестовом сервере. Тестовые процессы после проверок остановлены.

В пределах выполненных проверок регрессий turn LIFO, двух пасов, фаз combat,
боевых continuation и таймера не обнаружено. Stage 3 не начат и требует отдельного
согласования пользователя.
