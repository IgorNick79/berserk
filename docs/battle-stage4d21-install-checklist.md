# Stage 4D.2.1 — проверка установки обязательного журнала

Эта инструкция заменяет выборочный запуск Stage4D.2. Журнал не требует конфигурации, room IDs, game IDs или приглашений. Старые `control_room_ids`, `recording_enabled`, `record_game_ids`, `journal_enabled`, `journal_game_ids` игнорируются; их можно удалить при плановом редактировании локального файла. Сам файл нужен только при использовании отдельных возможностей Replay Preview. Не включать preview для этой приёмки.

Перед ручной выкладкой проверить backup и наличие существующих пяти `battle_history_*` tables и `battle_command_journal`. Новых SQL/migrations у этапа нет. Оба DB principals (обычные игровые запросы и транзакция lobby acceptance) должны иметь необходимые DML права на games, Command Journal и историю; writer должен читать cards. Не подавлять ошибку отсутствующей таблицы/прав и не обходить writer.

Загрузить полный runtime diff этапа вместе: HistoryRuntime, HistoryRepository, Recorder, GameState, GameRepository, Lobby/MatchCreator, View/Screen/Battle/InfoPanel, index.php, battle-journal.php, retired journal-access.php. Удалить неиспользуемый ExperimentalHistory.php. JournalCardNames.php из предыдущего этапа должен оставаться. CLI journal_access.php больше не выдаёт доступ. Частичное обновление этих файлов не является поддерживаемой установкой. Учитывать OPcache по штатной процедуре хостинга.

1. Войти двумя разными аккаунтами в независимых браузерных сессиях.
2. Создать обычную новую комнату и принять второго участника. Ничего не настраивать для журнала.
3. Проверить наличие metadata и `journal_schema=1` новой партии, затем пройти подготовку/расстановку.
4. Открыть журнал обоим участникам. Выполнить движение, обычный удар, ACK результатов и конец хода. Проверить live-обновление, имена известных карт и скрытую проекцию.
5. Обновить страницу, временно оборвать соединение, восстановить его: история должна совпасть с уже сохранённой, без дубликатов.
6. Постороннему аккаунту чтение того же URL должно быть запрещено; `side` и иные дополнительные query-параметры не выбирают проекцию.
7. Завершить матч и проверить чтение истории обоими участниками после повторного входа.
8. Повторить создание quick-game; проверить наличие начальных строк без ручного разрешения записи.
9. Старую партию без истории не преобразовывать: отсутствие журнала не должно создавать новые исторические строки. Старые сохранённые проекции не пересчитывать.

При ошибке записи состояние игрового действия не должно подтверждаться. Диагностировать транзакцию, SQL права, доступность и место в БД; повтор/обновление состояния использовать по существующему Command Journal. Не выдавать успешный ответ при неподтверждённом COMMIT, не отключать журнал и не продолжать партию мимо записи. Production fault injection не нужен: откаты уже проверены в изоляции.

Доказательства и точные границы проверки: `battle-stage4d21-mandatory-journal.md`, `evidence/stage4d21-mandatory-journal/`. Код этого этапа автоматически не разворачивался.
