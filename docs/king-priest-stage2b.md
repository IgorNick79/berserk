## Исполнение

`action:memory_loss` проходит обычный `ActionResolver::handle()`: проверяются
ход, отсутствие незавершённого сражения, принадлежность, поле, жизнь,
открытость, блокировки, effective action, наличие монеты, флаг использования,
тип/жизнь/зона цели и обычные защиты impact. Затем существующий общий код
списывает `action.coins = 1`. В `resolveImpact()` вызывается готовый
`EffectiveFeatures::applyMemoryLoss()`, выставляется флаг использования и
выполняется обычное закрытие источника. Используется обычный экран результатов
impact и его ACK; броска кубика и урона от этого воздействия нет.

`action:heal` использует существующий `resolveHeal()` без изменений:
лечение ограничивается ранами, монеты не расходуются, источник закрывается.
Сохранены реакции «вместо лечения открыться» и «вместо лечения нанести раны»
с их существующим pending. После законного открытия лечение доступно снова.
Уже разрешённое лечение не отменяется последующим подавлением лекаря;
отложенная реакция цели проверяет effective features самой цели.

Выбор цели для этих обычных действий — клиентский выбор по ID до команды
`action`, а не отдельный серверный pending. После reload окончательная команда
повторно проверяет источник и цель до оплаты. После разрешения reload сохраняет
обычный ACK. Отдельного pending, механизма оплаты или продолжений не добавлено.
Повтор до/после ACK не обходит закрытие; открытие не сбрасывает лимит воздействия.
Дедупликация ID команды и CAS используются штатные.

## Состояние и жизненный цикл

* Использование: `source.flags.memory_loss_used = true`, на экземпляре карты.
  Сериализуется существующим GameState без нового формата сохранения.
* Воздействие: существующая связь
  `target.flags.memory_loss_sources[source.instanceId] = true` из Stage 2A.
* Смена хода, открытие/закрытие, перемещение и dying источника не снимают связь.
  Выход из field/flying снимает её по принятой границе ZoneManager.
* Уход цели снимает её воздействие, но не возвращает использование источнику.
  Уход одного из нескольких источников сохраняет связи остальных.
* Существующие полные очистки flags в кладбище/изгнании, воскрешении и
  инкарнации теперь сохраняют ровно `memory_loss_used`. Другие flags очищаются
  по прежним правилам. Карты без нового флага проходят те же очистки, что раньше.
* Обычные переходы зон, воскрешение и инкарнация сохраняют instanceId.
  Проверены наземный и летающий варианты обоих маршрутов. Использование после
  возврата не возобновляется; старая связь не восстанавливается автоматически.
* В ProphecyProcessor отдельно существует перенумерация показанных карт колоды
  при скрытии. Это не создание нового экземпляра при переходе на поле:
  перенумеровывается тот же объект с сохранением flags. Этот механизм не менялся.

Исходные prop/modifiers при наложении не изменяются. Все 13 постоянных ключей
сохраняются; остальные особенности проецируются принятым Stage 2A механизмом.
Базовые hp/hpMax, move/moveMax и значения удара не изменяются воздействием.
Броня использует принятый расчёт `CardStats::computeArmor()`: `prop.armor` и
модификаторы armor являются особенностями и подавляются как уникальные.
Самостоятельного исходного параметра базовой брони помимо этого расчёта
текущий конструктор боя не задаёт. Новый способ хранения брони не вводился.

## Итоговый prop

```json
{
  "save_coins": true,
  "actions": [
    {
      "key": "memory_loss",
      "name": "Потеря памяти",
      "type": "impact",
      "effect": "memory_loss",
      "coins": 1,
      "once_per_battle": true
    },
    {
      "key": "heal",
      "name": "Излечение на 2",
      "type": "heal",
      "value": 2
    }
  ]
}
```

`effect: memory_loss` — новый обработанный вариант существующего impact.
`once_per_battle` обозначает правило action, а проверку обеспечивает
MemoryLoss по сериализуемому флагу. Для лечения этот флаг не проверяется.
Новых классификационных полей постоянных/уникальных особенностей нет.

## Реальная SQL-интеграция и границы результата

PHP 8.1.9 CLI + mysqli, MariaDB 10.8.4/InnoDB, loopback port 33991,
datadir `stage2a-final-validation/mysql-data`: повторно использована
исключительно сохранённая одноразовая копия тестовой БД. Production config
не загружался. Тест перед записью проверяет фактические port/datadir/InnoDB.

Обе способности проверены через настоящий `GameRepository::executeLockedCommand`,
предварительную регистрацию команды, реальный старт боя и обязательный live
Recorder. Проверены:

* Сохранение и чтение стоимости, закрытия, hp, связи и флага использования.
* Откат всего действия при невалидном JSON, реальной SQL-ошибке 1406
  и невозможности дописать обязательный журнал.
* Успешный retry того же processing command после каждого отката.
* Дедупликация committed ID без повторного исполнения и отказ новой команде
  после ACK при закрытом источнике.
* Событие `ability.applied` в настоящем live journal для обеих способностей.
* Неизменность структур SQL-таблиц по SHOW CREATE TABLE до/после теста.

Доказательства: `stage2b-validation/results.json`, `lint.json`,
`source-integrity.json`, `environment.json` в корне рабочего пространства.
Сопоставлены хеши PHP src/tools и JSON карты с проверенной копией.
PHP lint и git diff --check проходят. Одноразовый SQL-сервер после проверок
остановлен.

FPM/HTTP не выполнялись: php-fpm и активные php-cgi workers не обнаружены.
Проверка повторов выполнена на серверном пути command journal из CLI, а не
отправкой HTTP-запросов. Не проверялись браузерное отображение, реальная
сетевая доставка команд и Oracle MySQL. UI не изменялся: сервер блокирует
использованное действие и не возвращает его цели; отдельное оформление
состояния «уже использовано» не добавлялось.

Решение о практическом тестировании и внесении prop в БД остаётся за Project Lead.
Дополнительные этапы не начаты.
