# Stage 3.9R — включение и ручная проверка «Играть с ботом»

## Статус

**Локальный стенд готов к ручному playtest.** Прошли 39 HTTP/SQL и браузерных контролей, 45 регрессионных наборов, 743 позиционных контроля и целевые Engine/SQL-проверки main, before/after и «Пророчества». Четыре прежних сбоя воспроизвелись отдельно: `test_bulbagur`, `test_lucktest_manual`, `test_lucktest_quick`, `test_stage31_fixes`. Все 527 исходных хешей совпали, включая постоянный журнал партии 0. Миграция появилась в итоговом списке из-за исключения Git и сверена с 3.9Q.

Публичный production не затрагивался. Указанного общего staging-адреса и доступа к нему в задании нет. Проверена локальная disposable среда с отдельным MariaDB/InnoDB и настоящим Edge/Chromium на loopback. После автоматического прогона стенд останавливается. Для ручного сеанса его можно запустить с удержанием процесса по инструкции ниже. Ручная приёмка Project Lead остаётся отдельным шагом.

## Готовность миграции и конфигурации

В рабочем дереве присутствует 3.9Q: `LobbyStore::createBotMatch`, отдельный серверный маршрут, маркер комнаты, `BotMatch` и AJAX-фрагменты существующего боя. Миграция добавляет три nullable-колонки в `lobby_rooms`: `bot_account_id`, `bot_visited`, `bot_diagnostic`. Stage 3.9R добавил узкое исключение в `.gitignore`, поскольку глобальное `*.sql` скрывало новую миграцию. Engine, Planner, настройки боя, авторизация и UI 3.9Q сохранились.

Проверка начиналась с уже созданного PvP на старой схеме. После ALTER сохранённые JSON и версия совпали, оба участника сохранили доступ. Прямой повтор ALTER ожидаемо получил ошибку duplicate column без изменения партии. Воспроизводимый повтор развёртывания выполняется через preflight, который пропускает ALTER при наличии всех трёх колонок. Смешанное или несовпадающее состояние схемы требует разбирательства до включения.

Аккаунт бота создаётся обычным серверным AuthStore с нераскрытым случайным паролем. Его ID указывается положительным целым в закрытом `config/auth.local.php`. Аккаунт не получает отдельного пользователя БД или чужой стороны. Сервер проверяет назначение `player` в приватной комнате, связанную игру и актуальную версию. Обычная HTTP-сессия виртуального аккаунта в bot-месте отклоняется. Отключённое значение, строка вместо числа, отсутствующий аккаунт и совпадение с человеческим аккаунтом отклонены без новых комнат и игр. В ответе создания передаётся адрес игры. Секреты оператора в артефакты не записывались.

## Проверка боя

Edge прошёл создание приватной партии, передачу трёх ходов человеком, ответ бота, удар и обязательное подтверждение результата. Фрагменты поля и финал сдачей обновились в том же документе. Reload сохранил ID. В отдельном браузерном матче с исходным синтетическим каталогом принято 77 человеческих команд. Браузер показал «Все ваши существа уничтожены», а InnoDB сохранила `game_over / elimination`. Первый прогон этого дополнительного сценария остановился на форме режима удара из-за селектора теста. Селектор исправлен в тесте, затем пройден полный матч. [Браузерный результат уничтожения отряда](evidence/stage-3.9r/natural-browser.png).

В двух вкладках открывался один ID. После их закрытия и завершения текущих запросов проверено, что версия оставалась прежней. После открытия сохранённой ссылки возобновилась синхронизация. Бот выполняется только от авторизованного polling и ограничен четырьмя решениями на запрос. Новое решение строится после commit из перечитанного состояния. Отдельные сессии одного host повторили конкурентные запросы без двух commit на одну версию. Отклонены внешний аккаунт, устаревшая версия и конфликт payload. Проверены потеря poll и потеря ответа на уже сохранённый POST с восстановлением через журнал. Откат записи сохраняет состояние, версию и память перемещений.

Обычные PvP-комнаты и бой проверены отдельно. Откат подготовки при обязательном окне сохраняет прежние комнаты и партии. Контроли точных v3 «Пророчества» повторили исключение начатых reorder и summon. Известный серверный обход прямого `close_prophecy` сохраняется. Перед публичным выпуском нужен отдельный серверный guard, который учитывает текущую стадию и предлагает только штатный способ завершения, затем транзакционные отрицательные проверки owner, версии и сохранности pending. Допуска для публичного API этот аудит не даёт.

Forced-strike/Smart остаётся известным тактическим пределом 3.9O. Работоспособность браузера проверена в нескольких последовательных ходах. Точный долгий forced-strike/Smart застой в браузере на этом этапе отдельно не воспроизводился. Автоматического завершения за отсутствие прогресса нет.

## Развёртывание и откат для оператора

1. Выбрать разрешённый staging с отдельными БД, auth-конфигом и аккаунтами. Сделать резервную копию и сверить сервер, схему, `ENGINE=InnoDB`, наличие прежнего wizard-индекса `uq_lobby_creation` и ограничений комнат. Оставить `bot_account_id=null` на время обновления.
2. Проверить колонки в `INFORMATION_SCHEMA.COLUMNS`. Ноль из трёх — применить [миграцию 3.9Q](../tools/migrations/20261108_bot_matches.sql) один раз. Все три — сверить типы, NULL и пропустить ALTER. Частичное наличие — остановиться и выяснить состояние схемы. Перепроверить существующую PvP-партию и права чтения.
3. Развернуть 3.9Q. Для отдельного gameplay-подключения нужны существующие права чтения комнаты и право `UPDATE` только для `bot_visited` и `bot_diagnostic`. Lobby-подключение использует прежние INSERT/UPDATE комнат. Создать отдельный аккаунт штатной регистрацией AuthStore, сгенерировать нераскрываемый случайный пароль, указать ID в закрытом конфиге. Пароль не нужен для исполнения и не передаётся участнику. Не давать этому аккаунту debug-доступ.
4. Проверить вход человеческим аккаунтом, создание, ход, собственное обязательное окно и возврат по сохранённой ссылке. Повторный запуск процедуры проверяет существующую схему и использует тот же стабильный ID. Для отключения выставить `bot_account_id=null`. Существующие bot-партии после отключения перестают автоматически продвигаться. Оставить nullable-колонки и данные. Для полного отката стенда восстановить согласованный снимок кода, конфигов и базы. DROP колонок на используемой базе в процедуру отключения не входит.

## Ручной сценарий Project Lead

- В разрешённом staging открыть `/lobby.php` после входа человеческим аккаунтом. Для локального стенда сделать копию проекта под TEMP с assets и без приватных конфигов. В этой копии выполнить `$env:BERSERK_BOT_MANUAL='1'; python tools/test_bot_activation_http.py`. Когда скрипт предложит ручной сеанс, открыть [локальное лобби](http://127.0.0.1:33572/lobby.php), зарегистрировать тестовый человеческий аккаунт и войти. Enter завершает стенд.
- Нажать «Играть с ботом». Появится приватный LuckTest. Человек — host, бот — player. Сохранить ссылку `index.php?game=…`. Сделать несколько ходов, подтвердить свой результат и проверить изменение поля. Для проверки двух вкладок открыть ту же ссылку, а затем закрыть обе и вернуться по ней.
- При сообщении unsupported сохранить ID партии, видимый текст окна, время, ожидаемое действие и скриншот. Если нужен протокол, приложить только безопасные сведения о статусе и версии. Не передавать cookie, CSRF и закрытый конфиг. Штатная сдача завершает матч.
