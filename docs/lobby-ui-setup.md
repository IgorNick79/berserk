# Лобби, настройка комнаты и меню игры

Ветка `codex/lobby-ui-setup`, основа `7c88219` (Stage 5E.2). Пункт о переносе боевого журнала снят пользователем: журнал и Recorder не изменялись.

## Поведение

- `/` и обычный `/index.php` переводят на `/lobby.php` до требования входа. Гостю доступен список игр; запись и доступ в комнату требуют авторизованный аккаунт. Не раскрываются GameState, CSRF участников, request ID кандидата или приватные игровые экраны.
- Справа в лобби — профиль: авторизация, регистрация и disabled «Забыли пароль» для гостя; профиль и POST/CSRF-выход для авторизованного игрока. Фон совпадает с подготовкой и боем, таблица прокручивается внутри страницы на узком экране.
- Создание: выбор вида → существующие элементы настроек → «Опубликовать игру» → ожидание. Просмотр и изменение мастера не создают комнат или матчей. Новые POST-create требуют явный `setup_mode` и валидируются на сервере.
- В таблице и комнате показаны вид игры и дата создания. Дата хранится в UTC, в браузере отображается локальное время. Значения `game_type`: `system`, `draft` (Grid), `solomon`, `sealed`.
- Настройки комнаты сохраняются в SQL до её публикации. При accept выполняется прежняя единая `RoomTransaction`: создание одного GameState, применение выбранного режима через существующий PrepareProcessor, запись JSON/status и привязка комнаты. Генерация Draft/Sealed начинается только после подтверждения кандидата; повторного экрана настройки нет. Ошибка подготовки откатывает матч и комнату. Каталог читается через существующий `config/db.php`; лобби не требует DDL/TRIGGER-прав.
- Существующие комнаты с NULL-конфигурацией сохраняют прежний выбор режима после accept; игровые данные не переписываются.
- «В лобби» перенесено первым пунктом меню. На подготовке, в бою и на завершённом экране доступны те же пункты меню, профиль и выход. Звук и коврик работают на подготовке и сохраняются для боя без продвижения таймеров/этапов. На завершённом экране изменение предпочтений отключено. «Отложить игру» остаётся прежней заглушкой, Debug отключён для аккаунтных игр согласно существующему запрету prototype-параметров.
- При пустом отряде «Подтвердить» — настоящий disabled-button. Подтверждение непустого отряда спрашивается внутри capture-перехватчика POST-транспорта: отмена не отправляет команду. Обработаны ссылки, формы с hidden cmd и формы с cmd в submitter. Тем же способом сохранены confirm для пересдачи и ручного завершения драфта.
- У `.field-cell` удалён базовый белый фон; выделения своих/чужих карт сохранены. `.field-cell.move-target` использует alpha 0.5.

## Схема и ручная подготовка

Новая добавочная миграция: `tools/migrations/20261021_lobby_setup.sql`. Её необходимо отдельно проверить и выполнить вручную **до включения нового создания игр**. В текущей задаче production SQL не выполнялся.

Миграция добавляет в существующую `lobby_rooms` nullable `game_type`, nullable `setup_json` (LONGTEXT) и индекс `(game_type,state,created_at)` для будущей фильтрации. Старые строки остаются NULL; backfill, TRIGGER, пересоздание таблиц и изменения `games` отсутствуют. Миграция выполняется один раз после inventory; при существующих/частично добавленных колонках нужно остановиться и проверить схему. Исходные CREATE 5A/5B и аудит MySQL 5.7 не изменены.

Сервер проверяет тип, числовые поля, формат параметров и ограничения через существующие GameSettings. При accept проверяется согласованность SQL `game_type` и сохранённой конфигурации. CHECK на MySQL 5.7 не используется как защита. Без новых колонок публикация не сможет завершиться, вставленная строка комнаты будет откатана.

## Проверка и ограничения

Лаборатории используют изолированные локальные MySQL 5.7.39 / MariaDB 10.8.4 и PHP 8.1.9; это не тест точных production PHP 8.4.5 / MySQL 5.7.30. Материалы: `docs/evidence/lobby-ui/`. Команды:

```text
python tools/test_lobby_ui_integration.py mysql57
python tools/test_lobby_ui_integration.py mariadb108
python tools/test_lobby_ui_lobby.py mysql57
python tools/test_lobby_ui_lobby.py mariadb108
node tools/test_prepare_confirmation.cjs
```

HTTP-проверки охватывают все четыре вида игры, отсутствие GameState до accept, rollback при ошибке генерации, SQL/JSON-участников, повторное принятие, публичный список, запрет гостевой записи, CSRF и изолированное изменение звука/коврика. Браузер проходит создание из мастера, два аккаунта, меню, выбор отряда с отменой/принятием confirm, расстановку, бой и завершение; проверяет прозрачность клеток. Дополнительный Lobby suite проверяет гонки, откаты и unknown COMMIT.

В двух прогонах MariaDB старый случайный `test_settings_flow.php` упал на `confirm_settings` для random Draft (строка 318 — discrete, строка 301 — continuous). Сохранён `mariadb108/integration-regressions-first-run.json`; этот результат нельзя считать зелёным или исправленным данной UI-задачей. Engine, PrepareProcessor/Draft и сам `test_settings_flow.php` относительно 5E.2 не менялись. В отдельной изолированной лаборатории запущен pristine `src` и тот же тест из исходного релиза `7c88219`: три фиксированных диагностических запуска прошли (см. `baseline-settings-flow.json`). Поэтому воспроизводимый baseline-регрессор пока не получен; нельзя утверждать доказанную первопричину или считать проблему исправленной. Сбой требует отдельного исследования входных наборов/случайности, а не скрытого повтора accept или ослабления ограничений копий.

Production SQL, push, merge, SSH и deploy не выполнялись. Исторические release ZIP/manifest/evidence Stage 5E.2 не заменяются новым UI-кодом. Private configs, sessions, storage/games и пользовательские данные не удаляются; собственные временные лаборатории очищаются после проверки.
