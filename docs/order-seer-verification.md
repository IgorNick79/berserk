## Реальный HTTP с изолированным хранилищем

`python tools/test_deck_reorder_http.py`: PASS. Запускает PHP loopback-сервер на свободном порту, две независимые cookie-сессии, временный JSON-файл под эксклюзивной блокировкой. Не загружает конфигурацию БД. Сервер останавливается, временные файлы удаляются.

Внутри fixture используются настоящие Engine, TurnPhaseProcessor, ChoiceRegistry, GameState и BattleSnapshotRenderer. Пройден end_turn противника → offer → show → view → next(bottom) → order → pick → finish → закрытие pending → активный игрок player. После каждого шага проверяется повтор той же команды. Проверено наличие имён и изображений трёх карт только в snapshot владельца и отсутствие их в snapshot противника. Состояние между HTTP-запросами восстанавливается из JSON.

Это HTTP-fixture с настоящим движком и renderer, а не www/index.php с production-аутентификацией, CAS и журналом команд InnoDB. Этот инфраструктурный путь не проверялся; рабочая БД не использовалась.

## Точки интеграции и исправления

DeckReorderProcessor использует ProphecyProcessor::peek. Стадии offer/view/order хранятся в pending_deck_reorder с ID, revision, owner, выбранным направлением и списками selected/remaining. Финальный порядок применяется атомарно; первая выбранная карта оказывается у соответствующего края. Случайно переставляется только remaining. Команды валидируют владельца/ID/ревизию.

TurnPhaseProcessor добавляет адресную задачу deck_reorder в существующую пассивную очередь конца хода противника. После pending вызывается штатный resume. Другие opponent_turn_end эффекты остаются отдельными задачами.

DeckReorderChoice использует существующий prophecy_card.tpl. Исправлено отсутствие изображений: добавлено необязательное image_html в общий шаблон; его другие вызовы сохраняют прежний вид. Кнопки и подписи содержат ID экземпляров. В GET-форме сохраняются параметры исходного маршрута. Противнику выдаётся только ожидание; диагностический pending в BattleScreen редактируется до owner.

Конфигурация для ручного добавления: docs/order-seer.prop.json. ЗОВ и активный разряд используют существующие prop-механизмы.
