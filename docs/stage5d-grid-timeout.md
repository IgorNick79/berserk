# Stage 5D — диагностика Grid timeout

Вердикт: воспроизведён существующий дефект continuous Grid, блокирующий выпуск всех режимов. PrepareProcessor, DraftProcessor и правила не изменены. Это не исправленный дефект; требуется отдельное разрешение Lead на исправление правил/процессора.

## Вход и воспроизведение

Исходные `evidence/stage5c/grid-timeout-fixture.json` и `draft-timeout-diagnostic.json` сохранены без изменений. SHA-256 первого указан в `evidence/stage5d/grid-summary.json`. JSON корректен, synthetic_only=true, 100 карточных определений; все ukid из grid/pool/recycle/picked присутствуют в каталоге. Исходное состояние draft, Grid continuous/manual, picked 3/3, оба total budgets=600/600. Проверен roundtrip GameState::fromArray.

Команда: `php -n tools/test_grid_timeout_fixture.php`. Скрипт определяет test-only Db до autoload: только SELECT из frozen каталога, elements neutral, synergy пустая, любые другие запросы запрещены. Нет подключения к БД, config, SQL UPDATE или save. Результаты — `evidence/stage5d/grid-timeout-runs.json`; содержит начальные, промежуточные и конечные draft state, version, hashes полного GameState и events каждого вызова. Это модельный тест реальных неизменённых классов, отдельно от MariaDB/HTTP проверки.

Test-only namespaced random_int использует mt_rand для фиксированных seeds; shuffle использует тот же seeded MT, time фиксирован, `$now` передаётся явно. Эти функции существуют только в отдельном CLI процессе теста, приложение их не загружает. Первые 5 прогонов seed1701 дают одинаковые конечные hashes. Seeds12/42/43/51/77/87/92/95 воспроизводят guard failure. Отдельный failing_seed=12 повторён трижды: одинаковый hash и ошибка во всех трёх случаях. Ещё 50 прогонов используют настоящий random_int; доля сбоев в этой малой выборке не оценка production вероятности. Точные счётчики находятся в grid-summary.json.

Дополнительно проверены одинаковые входы до deadline, истёкший action при живых total budgets, один истёкший total, отсутствующий timer (runtime initialization), уже завершённый draft. Каждый сценарий повторён трижды. После первого вызова процессора сделан второй с тем же временем: terminal остаётся view; failing_seed остаётся ошибкой. Wall clock, session, HTTP workers и состояние БД для детерминированного сбоя не требуются.

## Причина и промежуточное состояние

При seed12 после picks: host=30, player=29, pool/recycle пусты, на grid только card_15. У player уже 3 card_15, обычный лимит копий=3; ему нельзя взять последнюю карту. Host может вместить копию, но выбор оставит player без 30-й карты и блокируется isViableSelection. validSelections пуст для обеих сторон; pass/recycle повторяют ту же единственную карту. Через 500 итераций resolveDraftTimeoutsInternal возвращает `Таймаут драфта не смог выбрать допустимое действие`.

Continuous isViableSelection проверяет количество оставшихся карт и минимумы, но не полную возможность распределения оставшихся копий с учётом обоих лимитов. Поэтому случайные ранее допустимые picks могут привести к этому тупику. Это локализованная причина на frozen fixture; исходный промежуточный HTTP failure не сохранил RNG trace, поэтому тождественность каждой его случайной операции установить нельзя. Совпадает симптом: поздний read-only повтор того же исходного состояния мог выбрать другой путь и вернуть view.

При ошибке процессор уже изменил объект в памяти, но events возвращены пустыми. index.php draft_sync сохраняет только успешный результат с events; неудачная частичная последовательность не сохраняется. Исходные persisted picked3/3 поэтому совместимы с failed runtime picked30/29. Следующий sync пересчитывает от исходного состояния со свежим random и иногда проходит. Успешный повтор не означает устранения дефекта; HTTP draft_sync возвращает 200 с ok=false/error и частично изменённым in-memory state; код HTTP не доказывает успех.

## Решение для релиза

NO-GO для выпуска полного набора режимов. Нельзя маскировать ошибку повтором тестов или объявить Grid стабильным. Нужны отдельное разрешение, изменение алгоритма с доказательством допустимости распределения, regression на frozen seed12 и HTTP проверка сохранения/ошибок. Изменять только transport или выключать режим на UI недостаточно для серверного ограничения. Ограниченный выпуск без Grid возможен лишь после отдельного согласования и проверенного серверного ограничения; в этом этапе такого ограничения нет.
