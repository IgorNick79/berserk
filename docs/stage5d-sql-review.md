# Stage 5D — SQL review и ручная последовательность

Production не подключался. `tools/migrations/20261021_release_preflight.sql` — только SELECT/SHOW; проверен на изолированной MariaDB10.8.4 после установки схем (289 строк metadata, evidence/stage5d/sql-preflight-lab.txt). Не выводит accounts/password_hash values или games.json. Это операторский preflight: наличие metadata само по себе не PASS, сравнить с DDL и условиями ниже. На другой СУБД/версии отдельно проверить поддержку information_schema.CHECK_CONSTRAINTS и enforced CHECK.

## Согласование

accounts.id — signed INT AUTO_INCREMENT PK; login/login_key ascii_bin, UNIQUE login_key, CHECK ASCII syntax/lowercase, datetime(6). auth_login_attempts.bucket_key char64 ascii_bin PK, attempts unsigned INT, окно datetime(6), индекс времени. AuthStore нормализует display widths MySQL8, проверяет типы/nullability/коллации/ключи чтением.

lobby_rooms.id signed INT PK, version unsigned INT>0, game_id signed INT nullable UNIQUE. Четыре FK: creator/candidate/accepted→accounts.id и game_id→games.ind; без CASCADE. Индексы участников/state+updated. CHECK фиксирует точные open/awaiting_confirmation/started формы, различие creator и candidate/accepted, nullability полей в каждом состоянии. Авторизация actor/request/version выполняется также под FOR UPDATE. Кандидат не записывается в games до accept; games JSON и room link создаются в одной InnoDB транзакции. ID аккаунтов не считаются игровыми сторонами; legacy1/2 не мигрируют в аккаунты.

battle_command_journal — существующая схема из constructor перенесена без изменения полей в ручной CREATE. PK bigint unsigned; game_id INT signed; UNIQUE(game_id,player_key,command_id), status index. Новых FK нет, исходный контракт сохранён. games.version уже должен существовать (signed INT NOT NULL); runtime ALTER удалён, CAS/transactions не менялись. GameRepository и CommandJournalRepository теперь только проверяют схему. Поиск CREATE/ALTER/DROP TABLE и CREATE TRIGGER в src/www: совпадений нет.

Все три новые установочные миграции только CREATE, InnoDB; нет DROP/TRUNCATE/DELETE, изменения пользовательских строк, TRIGGER или требования TRIGGER privilege. Миграции не идемпотентны и DDL не атомарен: нельзя повторять поверх частичной установки. Старые chat/history схемы не содержат FK на accounts и не требуют переприсвоения старых отправителей. Их индексы и существующие CHECK сохраняются.
