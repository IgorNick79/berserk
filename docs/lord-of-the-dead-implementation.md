# Повелитель мёртвых — способности при инкарнации

## Результат

Добавлены конфигурационные реакции на успешную инкарнацию своего существа: автоматическое открытие источника и +1 движения получателю до конца следующего собственного хода. Использованы существующие openCard, modifiers, effectiveProp и счётчик истечения по концам ходов владельца. Новых pending, UI и изменений порядка инстантов нет.

## Файлы

- `src/Core/TurnProcessor.php` — две точки подключения успешной инкарнации и один общий приватный метод `applyAlliedIncarnationEffects`.
- `docs/lord-of-the-dead.prop.json` — предлагаемый полный prop, включая неизменённый действующий инстант.
- `tools/test_lord_of_the_dead.php` — 171 адресная проверка.
- `tools/test_lord_of_the_dead_sql.php` — 70 дополнительных проверок на изолированной MariaDB/InnoDB, с обязательной проверкой порта и datadir.
- `docs/lord-of-the-dead-implementation.md` — этот отчёт.

## Точный предлагаемый prop

```json
{
  "instants": [
    {
      "key": "bone",
      "name": "Кость",
      "effect": { "type": "damage", "value": 1 },
      "target": "enemy",
      "trigger": "turn"
    }
  ],
  "on_ally_incarnation": {
    "open_self": true,
    "move_bonus": 1
  }
}
```

Существующего ключа реакции на успешную инкарнацию союзного существа не было; добавлен универсальный `on_ally_incarnation`, без проверок UKID. `open_self` и `move_bonus` работают независимо. Исходный массив `instants` считан SELECT внутри READ ONLY транзакции и сохранён без изменения значений. Рабочая БД не обновлялась.

## Lifecycle и открытие

`chooseIncarnationCell()` вызывает реакцию после успешного `toField`, восстановления HP, открытости, маркеров, flags и собственных abilities инкарнации, до `refreshArmor` и снятия записи из очереди. `incarnateFlyer()` вызывает её в аналогичной точке после `toFlying` и смены типа.

Реакция принимает только живое, не dying существо типа creature/fly на поле боя (field/flying). Источники должны быть живыми, не dying, находиться на поле боя и иметь того же owner. Их конфигурация читается через effectiveProp. Реакции на получение жетона инкарнации не используются: жетон/готовность/ожидание клетки ещё не являются успешной инкарнацией.

Каждый подходящий закрытый источник открывается через штатный `Engine::openCard()`. Уже открытый источник не переоткрывается и не получает лишний сброс флагов действий. Нет ресурсов, самостоятельного действия игрока или выбора. Ограничения и семантика открытия не расширялись.

## Движение и истечение

Результат всех действующих источников объединяется через max: два источника с move_bonus=1 дают ровно +1. На получателе хранится один штатный модификатор:

```json
{
  "stat": "move",
  "value": 1,
  "expire": 2,
  "timing": "owner_turn",
  "source": "host",
  "stack_key": "ally_incarnation_move"
}
```

Для второго игрока source равен player. stack_key отделяет данный бонус от независимых модификаторов движения; обновление этого бонуса не удаляет другие эффекты. При повторном применении заменяется только этот ключ и обновляется срок, без суммирования. Сам жизненный цикл инкарнации предварительно очищает старые модификаторы получателя.

Базовый moveMax не изменяется. effectiveMove получает бонус через существующие modifiers. Текущий запас move увеличивается на разницу нового и прежнего бонуса, как в существующей механике хлыста, без восстановления уже потраченного движения.

В конце текущего собственного хода `afterEndPhase()` уменьшает expire с 2 до 1; конец чужого хода его не меняет; в конце следующего собственного хода модификатор удаляется. Нумерация общего battle.turn не используется и не меняется. Срок проверен для host и player через реальные команды end_turn с reload между переходами. Следующее штатное восстановление движения уже не содержит этот бонус.

Последующее подавление или уход источника не отменяет предоставленный бонус: это сохранённый временный эффект, а не вычисляемая аура. Новый бонус подавленный источник предоставить не может. Подавление самого получателя подчиняется существующей системе effectiveModifiers, без специальных исключений.

Уход получателя на кладбище/в изгнание очищает бонус штатным ZoneManager. В текущих правилах смерть уже инкарнировавшейся карты ведёт в изгнание; повторная инкарнация того же экземпляра проверена дополнительно на синтетическом повторном входе в существующий lifecycle, без изменения правил изгнания.

## Повторы и продолжения

Для обычной карты успешный выбор потребляет существующую запись очереди; для летуна карта перестаёт находиться на кладбище. Поэтому повторный вызов processIncarnation не срабатывает для уже возвращённой карты. Повтор команды после полного завершения отклоняется, не открывая заново закрытый источник.

Для принятых команд защиту от retry обеспечивает существующий command journal, а от устаревшей версии — CAS. Отдельных новых идентификаторов событий, pending или изменений continuation не добавлено.

Полный сценарий проверен через Engine и настоящую очередь начала хода: открытый источник → выбор штатной «Кости» → выбор цели → pass → 1 рана и закрытие → подтверждение результата → инкарнация → +1 движения → автоматическое открытие. Урон, стоимость закрытия и зарезервированное использование инстанта происходят один раз; очередь и pending завершаются штатно. Сценарий также прошёл с сохранением и reload после каждой команды в SQL.

## Ограничения и расхождение исходного описания

**Текущая «Кость» не реализована как метание с дальностью 4.** Фактическая сохранённая конфигурация содержит effect.type=damage, а `Engine::applyInstantEffect()` проводит её как impact. В `InstantProcessor::isLegalTurnTarget()` для этого инстанта нет проверки дальности 4. Это обнаружено адресно при проверке обязательной последовательности. По прямому ограничению задания существующий инстант, его конфигурация, стоимость и маршруты выбора цели НЕ изменены. Реализованы только две пассивные реакции. Если требуется привести инстант к тексту карты, это отдельное решение Project Lead.

Схема SQL, Recorder, InfoPanel, инстанты и общая система инкарнации/подавления не менялись. В рабочую БД не было записей. Интеграционные записи выполнялись только в сохранённом тестовом datadir; тестовый сервер привязан к localhost и после проверки остановлен. Для запуска сохранённой тестовой базы потребовался временный --skip-grant-tables; постоянные настройки и учётные записи не изменялись.

Commit/push не выполнялись. Реализация ожидает решения Project Lead и самостоятельного применения prop.
