Дата: 2026-10-19. Ветка: `codex/battle-chat`, основана на локальном `main` (`eb0a61e`).

## Согласованные условия

Идентичность остаётся прототипной: `first` = ID 1, `second` = ID 2. Проверяется участие выбранного ID в конкретном бою. URL позволяет выбрать любую из этих ролей; настоящей авторизации этот этап не добавляет.

## Поведение

Отдельные таблицы InnoDB `game_chat_messages` и `game_chat_reads`, кодировка utf8mb4. На каждое сообщение сохраняется серверный номер `games.json.battle.turn`, а при отсутствии номера — 0. Отправлять можно только в статусе battle. История остаётся доступной на экране game_over; повтор уже сохранённого request_id восстанавливает подтверждение даже после завершения боя.

Лимит — 1000 Unicode-кодовых точек после strip_tags. Пустые, некорректные UTF-8 и сообщения из одних невидимых символов отклоняются. Частота — не более одного нового сообщения в секунду от участника в одном бою. Повторы с тем же request_id и очищенным текстом возвращают прежнюю запись; изменение текста под прежним ID отклоняется. Клиент хранит неподтверждённый запрос в sessionStorage, в том числе при обновлении страницы, и повторяет только по нажатию «Отправить». POST защищён сессионным CSRF-токеном. Вывод текста через textContent.

Серверные маршруты в `www/index.php`:

- GET `ajax=chat_messages`: game, first/second, необязательный after_id или before_id. Последняя страница — 50 сообщений; новые загружаются по возрастанию ID, старые — отдельными страницами. Ответ содержит has_more, latest_id, last_read_id, unread, can_send.
- POST `ajax=chat_send`: csrf, message, request_id. sender_id и turn_number из запроса не используются.
- POST `ajax=chat_read`: csrf, last_read_id. Курсор проверяется в пределах боя и обновляется через GREATEST.

BIGINT-курсоры передаются JSON-строками. Отправки сериализуются короткой блокировкой строки games: номер хода и запрет после завершения проверяются в одной транзакции с вставкой сообщения. games не обновляется, версия и JSON не сохраняются.

## Синхронизация и звук

Используется существующий HTTP/fetch-подход без WebSocket, сервисов и новых зависимостей. Чат опрашивается отдельно каждые 1,5 секунды, в скрытой вкладке — каждые 5 секунд, с таймаутом 10 секунд. Параллельные опросы одного экземпляра исключены. Отдельный цикл нужен, поскольку battle-sync при отправке/восстановлении игровой команды приостанавливается, а серверный battle_sync вызывает автоматическое продвижение боя. Запрос чата завершается до создания игрового репозитория/движка и вызова этих обработчиков. Никакие запросы чата не запускают дополнительный battle_sync.

Звук вызывает существующий `root.berserkTurnTimer.notify()`; сохраняются общие настройки mute и ограничения браузерного autoplay. Начальная история задаёт baseline и не озвучивается. Повторные страницы и собственные сообщения не озвучиваются. При переподключении уведомление получают только новые сообщения после baseline.

Прочтение записывается, когда панель открыта, вкладка видима и в фокусе, а история прокручена до нижнего края. Если пользователь читает старую часть истории, новые сообщения не отмечаются автоматически прочитанными. Последний прочитанный ID хранится отдельно для каждого участника.

- `test_game_chat.php`: 21 проверка — очистка HTML, UTF-8, эмодзи, пустота, лимит, курсоры.
- `test_game_chat_browser.cjs`: 95 проверок — два настоящих контекста Edge/Playwright, обмен и восстановление истории, подделка отправителя/хода, чужой бой, CSRF, лимиты, уведомления, серверное прочтение, pending и истёкший anchor без изменения JSON/версии/таймера, запрет отправки после боя, история после боя, 121 сообщение по страницам, Cancel, ширины 1600/800/375.
- В том же сценарии: потеря HTTP-ответа после реального COMMIT, обновление страницы и безопасный повтор; offline/reconnect без повторного звука; три параллельных PHP-процесса (два одинаковых запроса и противник) без потери/дублей; обычный battle_sync одновременно с чатом; монотонность прочтения при запоздавшем запросе.
- Регрессии: turn timer — OK; match pause — 119 assertions; sound client — 36 checks; deferred sound fallback — 16 checks; shared resume sound — 84 checks.
- PHP lint, Node syntax и git diff --check проходят.

Визуально просмотрен мобильный скриншот. Снимки трёх ширин сохранены в `C:/Users/mi/Documents/Berserk/battle-chat-tests/`. В тестовой копии не копировались изображения поля и карт; проверялись геометрия панели и её реальное DOM-поведение.

Для повторного браузерного прогона нужна отдельная копия исходников без .git с конфигурацией БД `berserk_chat_test`, уже применённой миграцией и loopback HTTP-сервером. Окружение: CHAT_TEST_URL (http://127.0.0.1:PORT/index.php), CHAT_TEST_DATADIR (точный datadir тестовой БД), PHP_BINARY, PLAYWRIGHT_MODULE, BROWSER_EXECUTABLE. CHAT_SCREENSHOT_DIR необязателен. Фикстуры отказываются работать без совпадения имени БД и datadir. Сценарий также проверяет, что HTTP обслуживает именно эту копию исходников.

## Подключение к игровой БД

Настроенная локальная игровая БД во время работы недоступна. В неё ничего не записывалось. Перед применением миграции нужно подтвердить через SHOW COLUMNS, что `games.ind`, `host_id`, `player_id` имеют тип signed INT: миграция подготовлена для этих типов, а код проекта использует целочисленные ID. Проверка на реальной БД из-за недоступности не выполнена.

После резервного копирования и проверки типов применить `tools/migrations/20261019_game_chat.sql`. Автоматического создания таблиц на пользовательских запросах нет. До применения миграции чат сообщает о недоступности и повторяет подключение; боевые запросы продолжают работать независимо.
