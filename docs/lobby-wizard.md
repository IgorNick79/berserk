# Трёхэтапный мастер создания партии

Дата: 30 октября 2026. Реализация и результаты локальных проверок. Production deploy и миграции рабочей БД не выполнялись. Публикация в Git — для самостоятельного pull оператором.

## Поток создания

Ранее экран лобби последовательно показывал выбор режима и его настройки через отдельные GET-переходы. POST создавал комнату; запись игры появлялась после заявки второго игрока и подтверждения создателем.

Новый `LobbyWizard` объединяет выбор режима, общие настройки и параметры режима в одной форме. Переключение шагов не создаёт комнату или игру. Финальный POST использует прежний контроллер, `RoomSetup`, `LobbyStore`, `RoomTransaction` и подтверждение участия. Поля режимов сформированы существующим `SettingsScreen`, серверная валидация сохранена. По умолчанию выбраны Sealed, открытая партия и отсутствие таймера.

Поля каждого режима имеют отдельного HTML form owner; неактивные поля отключены, их значения сохраняются при переключениях. Исправлена коллизия селекторов навигации со степперами настроек. Независимые radio-группы сохраняют значения и при начальном разборе HTML. Общие параметры сохраняются при смене режима.

Мастер использует существующий фон и центральную панель лобби. Верхняя навигация действительно sticky внутри единственной прокручиваемой области, нижняя навигация остаётся видимой. Применён единый `GameMenu` с контекстом `preparation`, включая ссылку «В лобби».

## Доступ и защита от повторного создания

Открытые комнаты сохраняют прежнюю процедуру участия. Закрытая комната содержит стабильный ID приглашённого аккаунта. Никнейм разрешается через существующий уникальный нормализованный ключ аккаунта: неизвестный аккаунт и приглашение самого себя отклоняются. Предварительная проверка выполняется до последнего шага, затем сервер повторяет её при создании.

Сервер фильтрует список, проверяет детали и действия под блокировкой, а также приглашённого перед созданием игры. Гости и посторонние не видят закрытую комнату и не могут присоединиться прямым HTTP-запросом. Существующее подтверждение создателем сохранено; после отказа приглашение остаётся привязанным к тому же аккаунту.

Случайный `creation_key` сохраняется на время формы. Уникальный индекс `(creator_account_id, creation_key)` защищает от повторного создания; повтор с теми же параметрами возвращает ту же комнату, с изменёнными — 409. Клиент блокирует повторную отправку во время запроса.

## Таймер и согласованные зависимости

Настройка партии: `settings.battle.turn_seconds`. Новые партии: 0 или 180; отсутствие поля в исторических данных означает прежние 180 секунд. Таймеры драфта не изменены. При 0 существующий `TurnTimer` не создаёт период, не считает время и не выдаёт событие истечения.

`MatchPause` сохраняет подтверждение второго игрока, лимиты, cooldown и длительность паузы, но допускает отсутствие часов. При возобновлении отключённый таймер не запускается.

Запись начала хода отделена от часов. Для отключённого таймера используются сохранённые `untimed_start_pending` и `untimed_start_recorded` с идентичностью `turn:owner`. Существующий hook `Engine::afterStartPhase()` дополнен проверкой незавершённого начала хода. Условие `start_resolution` для партий с таймером и порядок игровых обработчиков сохранены. Повторная загрузка и повторные запросы не создают вторую запись Recorder.

10-секундное информационное ожидание использует прежние `wait_id`, поколение, `started_at` и `deadline_at`. Для партий с таймером сохранена привязка к прежнему `period_id`, включая старый формат записей. Без таймера запись привязана к сохранённому номеру хода и его владельцу. Владелец берётся из существующего периода инстантов, поскольку в конце хода `active` уже может указывать на следующего игрока; для состояний без периода используется `active`. Фиктивные часы не создаются.

Продолжение выполняется прежней командой `confirm_strike` через существующий HTTP-производитель автоподтверждений и журнал команд. Проверки актуальности, повторного подтверждения и обязательных pending сохранены. Ручное подтверждение закрывает автоматическое обязательство. Пауза сохраняет идентичность ожидания и оставшиеся секунды; после возобновления применяется прежнее правило сдвига дедлайна. Исторические окна без временных меток не получают выдуманного времени начала и сохраняют прежнее ручное подтверждение.

## Миграция

Подготовлен `tools/migrations/20261030_lobby_wizard.sql` для БД лобби/партий: `lobby_rooms.invited_account_id`, `creation_key`, уникальный индекс и внешний ключ приглашения. Это отдельная миграция от ранее согласованных настроек аккаунта.

Существующие строки с NULL приглашением остаются открытыми. Перезапись JSON старых партий не требуется. SQL проверен только в одноразовой изолированной БД; перед активацией новой версии его нужно отдельно применить к соответствующей БД. Рабочая БД не изменялась.

## Проверки и свидетельства

Итог: 176 HTTP/БД-проверок, 28 браузерных проверок мастера, 24 проверок единого меню, 9 PHP-прогонов и проверки синтаксиса прошли. JavaScript-ошибок нет.

Результаты сохранены в `docs/evidence/lobby-wizard/`:

- `core-checks.json`: регрессии таймера, пауз, Recorder, вложенных pending, инстантов и информационных подтверждений; проверка настроек без подключения рабочей БД.
- `http-checks.json`: HTTP/БД-проверки меню и настроек, пяти режимов, приглашений, серверного доступа, повторного создания, чтения состояния, пауз, ручного и автоматического подтверждения результатов.
- `wizard/browser-checks.json`: браузерные переходы, значения по умолчанию, переключение всех режимов, ошибки приглашения, сохранение общих настроек, sticky, мобильная ширина, отсутствие лишних созданий и ошибок JavaScript.
- `syntax-checks.json`: PHP lint, JavaScript/CJS syntax, Python AST и `git diff --check`.

HTTP-проверки используют отдельную копию проекта, временные конфигурации и новую MariaDB на порту 33571. Производственные конфигурации и БД не используются. Тестовая БД явно создаётся с UTF-8, чтобы проверять сохранение русскоязычных сообщений боя.

Дополнительные проверки информационного ожидания охватывают 0, 180 и исторические настройки, обоих владельцев хода, границу 10 секунд, восстановление состояния, устаревшие ID и ход, повторный ACK, вложенный выбор, смену active в конце хода, запрос/отклонение/подтверждение/завершение паузы. Через HTTP проверяются ручной ACK, два одновременных запроса автоподтверждения, последующие повторные чтения, единственная автоматическая команда в журнале и однократное завершение.

## Границы проверки

- Среда проверки: PHP 8.1, MariaDB 10.8, Edge/Playwright. Рабочая инфраструктура и её версии отдельно не проверялись.
- Все пять режимов проверены до существующего экрана подготовки. Полные партии от создания до победы во всех пяти режимах не проходились.
- Полный общий интеграционный прогон проекта не запускался; выполнен изолированный прогон релевантных сценариев и перечисленные PHP-регрессии.
- Автоматические проверки не заменяют визуальное ревью пользователем.
