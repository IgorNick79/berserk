## HTTPS, proxy и sessions — обязательный gate

AuthSession доверяет только server variable HTTPS=`on` или `1`. Legacy journal-access принимает только `on`. Для общего совместимого контура требуется **HTTPS=on у FPM** после настоящего TLS ingress. SERVER_PORT=443, REQUEST_SCHEME и X-Forwarded-Proto сами по себе не учитываются. Причина исторического HTTPS rejection на реальном hosting не установлена: к production доступа не было.

Если TLS завершается у reverse proxy: ingress очищает клиентские forwarded headers; backend закрыт для произвольных клиентов; webserver/FastCGI задаёт HTTPS=on только от доверенного TLS listener/из проверенной цепочки доверенных proxy. Конкретную настройку оператор согласует с провайдером и проверяет через FPM. Нельзя безусловно доверять HTTP_X_FORWARDED_PROTO или ставить HTTPS=on для публичного plain HTTP. Не отключать проверку и не включать allow_loopback_http в production. Пока доверенного сигнала нет — STOP.

Проверить BERSERKAUTH5A: Secure, HttpOnly, SameSite=Lax, Path=/, cookie без session ID в URL, HTTP не выдаёт действительную auth session, чужой forwarded header не помогает. Login меняет SID и csrf, старый SID не работает; logout удаляет cookie и principal. PHPSESSID legacy invitation не является auth. Сессии доступны всем workers одного приложения; files directory вне www, существует, service user может читать/писать, нет общего доступа другим сайтам. При нескольких backend нужен общий session store/согласованная маршрутизация и locking; это не проверено локальной лабораторией. Проверить обычный reload и следующий запрос через другой worker; нельзя завершать gate только успешным первым login.

Сначала закрыть все изменённые маршруты maintenance на webserver, затем сохранить диагностические логи и backup текущей БД/storage. Откатывать код только к проверенной безопасной версии, которая понимает account ownership, с теми же guards. Старый prototype index `?first/?second` запрещено открывать для account-owned игр.
