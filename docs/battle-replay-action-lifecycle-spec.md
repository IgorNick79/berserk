# Berserk — согласованные границы будущего Action Lifecycle Recorder

Решения Project Lead, Stage 3.2, 20 октября 2026. Статус: архитектурная спецификация, **без реализации Recorder**.

Этот документ имеет приоритет над предварительными вариантами Stage 1/2 и обсуждением H1 в отчётах Stage 3/3.1. Исследовательские отчёты и доказательства сохраняются как история проверки.

## Общие требования

Replay Step отражает новое подтверждённое игровое действие и сохранённое состояние поля. Root/cause может связывать несколько действий, но не вводит новые уровни сражений. Неравенство «HTTP-запрос = действие» сохраняется: действие может продолжаться через pending, а один запрос — завершить несколько действий.

Собственные обязательные последствия действия, включая относящиеся к нему инстанты, перенос ран и реакции, должны закончиться до его итогового кадра. Оставшийся выбор следующего самостоятельного действия сам по себе не мешает фиксации предыдущего. Неизвестные зависимости не считать завершёнными по отсутствию strike/pending.

Snapshots неизменяемы. Получение состояния и регистрация фактических событий не должны менять порядок исполнения движка. Будущее подтверждение events/snapshots должно быть атомарным с games и Command Journal; несколько captures одной команды допускают один COMMIT. Никакого повторного выполнения механик при просмотре.

## Окончательное правило Гидры

1. **Каждое завершённое сражение Гидры — отдельный Replay Step.** После него сохраняется snapshot фактического поля, включая актуальные closed, HP, зоны и статусы. До завершения собственных инстантов и обязательных последствий кадр не финализируется.
2. **Добровольный `attack_series_end` — самостоятельное игровое действие, изменяющее поле**, но не сражение. После подтверждённого End сохраняется отдельный snapshot с `closed=true`, очищенными flags серии и фактически полученными последствиями завершения.
3. Предыдущий snapshot удара не изменяется. Условная причинная идентичность серии не заменяет отдельные результаты боёв или End.
4. Если следующая команда — `end_turn`, кадр добровольного End остаётся самостоятельным шагом. Его нельзя объединять с переходом хода или заменять более поздним состоянием.
5. После завершения штатных последствий перехода хода сохраняется соответствующий итоговый snapshot по общим правилам. Само раннее изменение active/turn ещё не означает завершённый переход.
6. **Естественное завершение серии внутри последнего боя:** закрытие Гидры входит в итог этого боя; дополнительного End-step нет.
7. Дополнительного сражения, обёртки combat или искусственного уровня атак на End нет. Типы шагов могут различать `combat` и `series_end`, но это будущие semantic labels, не внедрённые команды/таблицы.
8. Повтор committed command_id возвращает прежний outcome, не создавая кадр заново. Rejected/conflict/failed и любой запрос без нового подтверждённого игрового действия не создают Replay Step. Новый command_id сам по себе также не доказывает новое действие.
9. `cancel_pending`, которое существующий AttackSeriesContinueChoice направляет в тот же chooseAttackSeriesEnd, при успешном добровольном завершении имеет ту же границу. Нельзя обходить проверку фактического outcome только по имени команды.

## Обновлённая матрица Replay Steps

| Действие | Момент capture | Кадр / отдельный шаг | Доказательство / ограничения |
|---|---|---|---|
| Первый/очередной бой Гидры | После всех его инстантов/обязательных последствий и штатной развязки, до следующего боя | Да: фактическое поле; может быть closed=false | Hydra/targeted/DB H1 проходят; не переносить автоматически на все комбинации props |
| Добровольный End | После успешного chooseAttackSeriesEnd и относящегося post-processing, в той же подтверждаемой команде | **Да, отдельный series_end**, closed=true | H1/DB H1: closed false→true; это действие, не новое сражение |
| End непосредственно перед end_turn | Та же граница End; затем отдельная граница завершённого перехода хода | **Два разных действия и состояния**, без изменения прошлого | H1/DB H1: между End и end_turn не было действий картами |
| Естественный конец серии | При окончании последнего боя с finishAttackSeries | Кадр боя уже включает closed=true, **без дополнительного шага** | Адресный natural-end и test_hydra |
| Повтор End с прежним command_id | Новый capture отсутствует | Нет дубликата | DB H1 проверяет retry и стабильную persistenceVersion |
| Отклонённый End/next, нет pending или terminal | Новый подтверждённый outcome отсутствует | Нет нового шага | Адресные guards/terminal tests; final-state по отдельному правилу |
| Гибель Гидры | Фактическая развязка вызвавшего боя/реакций | Кадр боя либо terminal; не исполнять новый End ради очистки | H1 death/terminal cases |
| Завершение матча | После фактически выполненной successful внешней команды, подтверждённой БД | Обязательный final-state; interrupted scopes не доигрываются | Не запускать Engine ради красивого кадра |

Предварительные выводы по остальным категориям из Stage 3 сохраняются: отдельные combat-инстанты — события без собственных кадров; targeted Вальхалла — кадр законченного применения при разрешённых зависимостях; no-target repeats и неаттестованные сложные зависимые цепочки допустимо объединять. R1–R3 меняют корректность исполнения, но не внедряют эти границы в runtime.

## Что остаётся Stage 4

Формат IDs, storage, recorder hooks, snapshot DTO, серверная фильтрация, dedup constraint и reader/viewer требуют отдельной реализации и проверки. В Stage 3.2 их нет. Совпадение состояний в простом end_turn, который завершился внутри одного запроса, не разрешает сливать подтверждённый End с ходом. Диагностические JSON tests являются доказательством состояний, не готовыми snapshots приложения.
