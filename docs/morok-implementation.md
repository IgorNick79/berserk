# Морок: реализация и проверка

## Согласованное правило

Уточнение Project Lead в чате заменяет противоречивый пример исходного задания: любой попавший удар по закрытому Мороку устанавливается в 1, включая удар с числовой силой 0 или 1. Промах не превращается в попадание. Снижение на 1 работает отдельно, только когда открытый Морок назначен защитником (`defender_id`), а не просто выбран целью.

## Изменённые и добавленные файлы

- `src/Core/CardStats.php`: условие `defender` для существующего `damage_reduction`, вычисляемая горизонтальная аура, применение существующего отображения категорий, числовая установка по закрытой цели.
- `src/Core/StrikeResolver.php`: аура на атакующий и ответный удар; числовая установка перед защитами и нанесением ран.
- `src/Core/ActionResolver.php`: аура и числовая установка в существующих маршрутах простого/магического особого удара (`tap`, `magic`) и УЧР; корректная классификация нулевого особого удара, превращённого установкой в 1.
- `src/View/Ui/ActiveCardEffects.php`: строка защитного бафа в существующей проекции активных эффектов.
- `docs/morok.prop.json`: точная предлагаемая конфигурация, без изменения БД.
- `tools/test_morok.php`: 314 адресных проверок.
- `docs/morok-implementation.md`: этот отчёт.

## Точный prop

```json
{
  "ovz": 1,
  "damage_reduction": [
    { "types": ["shot", "throw"], "value": 1 },
    { "types": ["strike"], "defender": true, "value": 1 }
  ],
  "closed_strike_value": 1,
  "horizontal_strike_reduction": true
}
```

`ovz` и `damage_reduction` переиспользованы. Для второго добавлено обобщённое условие `defender`. Новые ключи `closed_strike_value` и `horizontal_strike_reduction` не содержат имени карты и не требуют UKID. Отдельных классификаторов постоянных/уникальных особенностей нет.

## Механизмы и порядок

1. **Выстрелы и метания.** Существующий `ActionResolver::resolveDamage()` вызывает `CardStats::getDamageReduction()` один раз; вычитает 1 только для `shot`/`throw`, ограничивая результат нулём. `DamageResolver` повторно эту величину не вычитает. OVZ остаётся отдельным существующим механизмом.
2. **Назначенный защитник.** Условие `defender` проверяет текущие `defender_id`, `attacker_id`, тип `strike` и эффективную открытость карты через `combatClosed()`. Работает на стадии числового снижения, не исправляет HP постфактум. Закрытый Морок это снижение не получает, атакующий Морок тоже.
3. **Закрытая цель.** `closed_strike_value` устанавливает числовую величину после бонусов/снижений и перед существующими ограничениями/защитами. Не меняет категорию на weak. Существующий запрет броска защиты закрытой карты не менялся. Обрабатываются обычный, ответный, особые удары и УЧР; выстрелы, метания, разряд и прямые раны не затронуты.
4. **Аура.** `hasHorizontalStrikeReduction()` каждый раз просматривает актуальные экземпляры на поле: одинаковый ряд, разница столбцов ровно 1, допустимые границы 6×5. Источник должен быть живым, не dying, в зоне field и иметь эффективный `horizontal_strike_reduction`. Состояние открыт/закрыт на ауру не влияет. Получатель тоже должен находиться живым на поле. Фильтра owner нет: союзники и противники равноправны, каждый экземпляр в общей клетке получает эффект.
5. **Категории.** В обычном бою переиспользована стадия существующего `strike_reduction`: после выбора снижения и разрешённых инстантов, перед выбором числовой силы и её бонусов/снижений. Собственное отображение `strike_reduction` сохранено; аура сводит оставшееся попадание к weak, не создавая попадания из промаха. Она защищает также атакующего от ответного удара. В маршрутах особых ударов и УЧР выбирается существующее слабое значение из таблицы действия. Действие с фиксированным `value` сохраняет это значение при смене категории.
6. **Маркер.** `ActiveCardEffects` добавляет одну строку «Защитная аура: удары по карте сводятся к слабому». Существующий `LiveBattleCard` отображает её через общий маркер активных эффектов и подсказку. Новые иконки, UI-компоненты и постоянные модификаторы не создаются. При нескольких источниках строка одна. Она пересчитывается при рендере по тому же предикату, что бой, поэтому перемещение, появление/уход, гибель и подавление/восстановление источников сразу меняют следующий снимок/рендер.
7. **Потеря памяти.** Все новые чтения источников используют `effectiveProp()`. Существующий список `PermanentFeatures` сохраняет OVZ; четыре уникальные способности исчезают из эффективной проекции. Сырой prop не меняется. Подавление получателя само по себе не отменяет внешнюю ауру живого неподaвленного источника. Сериализация использует существующие поля; после reload аура вычисляется заново.
8. **Инстанты и раны.** `InstantProcessor` и его порядок `redirect → dice → power → value → setter → wounds` не изменялись. Числовая установка проходит перед применением уже разрешённого `damage_cap` и перед `DamageResolver`. Поздние бонусы ран и перераспределение ран не перезаписываются; проверены свет фонаря и существующий `redistribute_wounds` с reload. Новых pending нет.

## Обнаруженные ограничения существующего движка

**Асимметрия damage_cap.** В исходном коде атакующий удар ограничивается после бонуса, ответный — перед бонусом. Воспроизводимый пример: слабый ответ 2, бонус способности +3, `damage_cap=1` даёт 4; аналогичный атакующий удар даёт 1. Сохранён прежний порядок для остальных карт; добавлена адресная проверка на ответ 4. Для новой числовой установки по закрытому получателю установка и ограничение применяются после числовых модификаторов. Общий рефакторинг не выполнялся. Этот существующий спорный случай передаётся Project Lead.

БД, SQL-схема, Recorder, InfoPanel, архитектура pending/continuation не изменялись. Commit/push не выполнялись. Реализация ожидает решения Project Lead и применения prop.
