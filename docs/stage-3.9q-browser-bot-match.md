# Stage 3.9Q — «Играть с ботом»

## Архитектурный аудит

`index.php` направляет стартовый GET в `lobby.php`. Начальный список уже содержал выключенную кнопку. Комнаты создаёт `LobbyStore`, назначение участников и завершение подготовки выполняет `MatchCreator` внутри `RoomTransaction`. Штатный LuckTest `start_stage=battle` проводит выбор стороны, состав, Random-расстановку и подтверждение через обычные правила. После входа в бой GameAccess проверяет аккаунт, участников комнаты, SQL-колонки и сохранённое состояние. AJAX использует действующие `battle_command`, журнал, expected_version, locked executor и `battle_sync`. Повторное открытие игры использует тот же ID. Эти пути позволили обойтись без нового движка и экрана.

## Создание и исполнение

Кнопка отправляет CSRF-защищённый `create_bot` с ключом создания. В одной транзакции создаются приватная комната, назначение host/player и быстрый LuckTest. Дубликат ключа возвращает ID уже созданной партии. При ошибке, включая выход штатной подготовки в обязательное окно вместо боя, транзакция откатывается. Каталог, пропы, правила и штатная расстановка сохраняются. Обязательная подготовка вне поддержанного быстрого старта остаётся ограничением 3.9Q.

Host — вошедший пользователь. Player — отдельно заведённый серверный аккаунт. Маркер bot-привязки создаётся только серверным маршрутом. Пользователь не выбирает ID бота и не передаёт за него команды. Даже с тестовой сессией виртуального аккаунта gameplay HTTP закрыт для его bot-места. Комната и GameAccess продолжают использовать действующий контракт участия.

После авторизованного `battle_sync` выполняется до четырёх решений. Каждое использует свежие собственные Observation и LegalActions, действующий Planner и проверку GameAccess. Журнал получает идентификатор `bot:<persisted version>`; единственный владелец записи исполняет команду под блокировкой через Engine. История посещённых клеток обновляется в той же транзакции, в пределах логического периода. Чужое обязательное окно останавливает цепочку. Своя неподдержанная стадия сохраняет диагностический код с версией в комнате. Отказ команды остаётся в журнале. При неопределённом результате повторное применение исключается, а подтверждённый откат фиксируется как failed.

Действующий polling возвращает обычные фрагменты боя. Привязка отображается как «Соперник: Бот». Результат bot-партии рендерится существующим шаблоном в текущем документе. Клиентское обновление синхронизирует видимые карты, HP, статусы и обязательные решения через прежний renderer. При закрытой или скрытой вкладке фонового исполнителя нет. После возвращения или reload polling читает прежнюю партию и может продолжить работу.

## Проверки

Пройдены 28 проверок HTTP/SQL и браузерного сценария в изолированной MariaDB/InnoDB. [Бой](evidence/stage-3.9q/bot-battle.png) · [Результат](evidence/stage-3.9q/bot-result.png).

Browser E2E использовал Chromium/Edge и реальные HTTP-запросы. Человек открыл игру кнопкой, передал ход, получил ответ бота и подтвердил результат удара через `confirm_strike`. Проверка наблюдала более новую версию и фрагмент поля в том же документе. Отдельно имитировались потеря poll и потеря ответа на уже committed POST. Команда восстановлена по журналу. После reload ID партии совпал. `game_over` получен штатной сдачей с показом результата без reload. Естественное уничтожение отряда в браузере в этом прогоне не проверялось.

SQL/HTTP проверили разные аккаунты, отказ постороннему, запрет браузерного управления bot-местом, параллельное создание и polling, stale, duplicate, payload conflict, откат подготовки и откат записи команды бота. Проверен отдельный быстрый PvP LuckTest: обычное приглашение и подтверждение, доступ обоих аккаунтов, неизменная версия при контрольном polling и отсутствие bot-полей ответа. Целевые Engine/SQL прогоны повторили main, before/after, «Пророчество» и точные v3, включая запрет опасного отказа. Публичный серверный дефект прямого `close_prophecy` остаётся отдельной задачей.

Пройдено 45 регрессионных наборов и 743 позиционных контроля. Четыре baseline-сбоя учтены отдельно: `test_bulbagur`, `test_lucktest_manual`, `test_lucktest_quick`, `test_stage31_fixes`. Снимки и SQL выполнены в TEMP. Первоначальному стенду недоставало миграции настроек UI. В первом браузерном варианте итоговый фрагмент строился из старого состояния, что приводило к reload. Эти два случая исправлены и повторно проверены. Для сценария потери ответа тест ждёт завершения штатной принудительной синхронизации.

## Практическая проверка Project Lead

1. На тестовом сервере применить [миграцию](../tools/migrations/20261108_bot_matches.sql) до включения маршрута. Для gameplay-подключения нужны действующие права чтения lobby_rooms и `UPDATE` колонок `bot_visited` и `bot_diagnostic`. Для lobby-подключения сохраняются обычные права INSERT и UPDATE таблицы комнат.
2. Завести отдельный обычный аккаунт через существующий AuthStore с криптографически случайным одноразовым паролем. Не публиковать и не использовать пароль в браузере. В закрытом `config/auth.local.php` задать его положительный целочисленный ID как `bot_account_id`. Для текущих матчей ID сохранять стабильным. Миграция и provision рабочего сервера в этом этапе не выполнялись.
3. Войти человеческим аккаунтом, открыть лобби, нажать «Играть с ботом». Выполнить действие, дождаться ответа и пройти видимое обязательное окно. Перезагрузить страницу и сверить ID. Затем завершить игру. Для воспроизведения автоматизации запустить `python tools/test_bot_match_http.py` из отдельной копии под TEMP с копией assets и без закрытых конфигов. Скрипт создаёт собственную InnoDB и запускает браузер.
4. Известные тактические ограничения AI 1.0 сохраняются. Публичный выпуск всего API требует отдельной проверки серверной валидации `close_prophecy`.
